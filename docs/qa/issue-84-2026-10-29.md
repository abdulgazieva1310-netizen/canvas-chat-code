# Issue #84 QA evidence — 2026-10-29

## Acceptance coverage

| Requirement | Implementation and evidence |
| --- | --- |
| Define minimum relevant history | Two to five owned, completed, scored reports from one exact role/type/mode/starting-level/language group. Recurrence requires a practice topic in at least two different interviews, not multiple answers from one report. |
| Map recurring weaknesses to goals | Only recurring-topic evidence reaches the provider. Goals need unique, valid references from two reports whose cited answers share a practice topic. The provider prompt requests a concrete action and evidence-based rationale. Normalization covers case and whitespace; synonym inference is explicitly deferred. |
| Communicate insufficient history | Study UI explains the minimum and recurrence requirement. API rejects unscored/unrelated or insufficient evidence before a provider call, with actionable error messages. Existing plans remain readable. |
| Define refresh timing | New compatible completions produce a notice on the next history read, without generating or modifying a plan. Creating a new plan uses explicitly selected reports. Regeneration uses the original sources and resets completion only on success. Tests verify new results preserve existing progress and invalid regeneration preserves the saved plan. |

## Limits

Provider calls are mocked in regression tests; this is not a live evaluation of
generated coaching quality. Exact topic recurrence is deliberately conservative,
and citation validation cannot prove every generated claim. Source dates remain
visible; recency weighting and expiry are not introduced. Existing saved plans
are not migrated; current requirements apply to new generation/regeneration.
No database schema or new dependency is required.

See [the history, evidence and refresh policy](../learning-plan-history.md).
